## [v3.9.4] · 2026-04-05

### 决策事件：Rw边界修复 · P0技术债关闭

**触发**：calculator-v2.js 非对称中空路径高估（34–38dB段），业主可能拿到含错误隔音参数的招标文件。

**核查过程**：
- 发起五任务外部核查，来源：ift Rosenheim实测报告 + Guardian GlassTime手册 + ISO 10140/717-1标准文件
- 关键发现：非对称中空因250–500Hz吻合效应，实测Rw工程上限约32–35dB；夹胶中空起始点36–38dB
- 切换点决策：取35dB（保守原则，避免承包商以非对称中空勉强应付35dB需求）

**决议**：
- `rw_max` 封顶：非对称中空路径从36dB收回至34dB
- 切换点：Rw≥35dB切换至夹胶中空路径（`laminated_hollow` level 4）
- 三玻两腔限制：交通噪声场景从eligibleLevels排除，原因是Rw可达但Ctr差
- 防御性 `is_risk` 标记保留，未来数据异常时兜底

**修改文件**：`shared/budgetSpec.js` / `arbitrator.js` / `documentMapper.js`（补传noise_type）

**测试**：133/133 passing（含v3.9.4新增8条边界回归 AR05–AR12，超出原基线125/125） → v3.9.5 升级至 134/134

**原则确立**：引入ift/Guardian/ISO外部实测数据作为边界标定依据；国内GB/T 8485与ISO 10140/717-1体系一致，数据直接适用中国市场。

**开放项**：
- [x] 125/125 passing → 133/133 通过（含AR05–AR12）
- [x] noise_type空值默认行为 → 补加显式默认值 `noise_type ?? 'quiet'`
      + AR12覆盖，两份arbitrator.js同步修改

## 架构冲突识别 · sprint8 前期

### 决策事件：三方文档比对分析
**触发**：将现有代码与两份补充技术文档进行三方对比
**发现**：
1. 双玻璃推荐系统并存（预算驱动 + 性能驱动），无仲裁机制
2. `calcRw` 跨重叠变量存在双重计数
3. `size_level` 字段语义混用（不同窗型共用同一字段）

**决议**：
- 引入 `resolveGlassConfig()` 统一仲裁函数
- 重构 `calcRwRequired()`，明确变量边界
- Q8 合并窗型尺寸维度，保持问卷9题总量不变

**原则确立**：竞争推荐系统必须有显式仲裁逻辑，否则输出不可预测。

## 内容真实性验证 · sprint7 后期

### 决策事件：计算引擎交叉验证
**方法**：从PDF输出反向还原问卷输入，手工执行计算引擎，与系统输出对比
**发现的差异**：
1. 楼层/总楼层比值不可能（数据映射错误）
2. 噪声等级评级矛盾（同一场景两处结论不一致）
3. 风压计算值偏差（超出合理误差范围）
4. 禁用条款错配：A档文件错误包含B档要求条款

**决议**：建立交叉验证为标准验收步骤（不仅审阅输出，还要反向验证输入）

## 产品架构确认 · sprint 早期

### 决策事件：产品定性决策
- 问卷：9题生活化问题（非技术语言）→ 已锁定，不扩展
- 输出：四章PDF招标文件（技术参数 / 红线清单 / 验收标准 / 商家评审表）
- 数据链路：reportSnapshot 不可变快照（审计可溯源）
- 平台定位：工具，MVP阶段不做双边平台

### 决策事件：L1/L2商业模式设计
- L1（免费）：参数摘要卡，6项核心参数，即时生成
- L2（付费）：完整四章PDF，价格待种子用户验证后定
- L1设计原则：制造认知缺口，让用户知道"我需要什么"，但不知道"具体标准是否达标"

### 决策事件：前端术语锁定
- 「门窗需求定制」（非「问卷」）
- 「招标文件」（非「报告」）
- 理由：术语本身传递产品定位，影响用户心理预期
