## PLAY-01：验收评审

### 适用场景
每次sprint结束、功能上线前、重大修复后。

### 执行步骤

**Step 1：甲方视角（权力转移效果）**
检查清单（18项，以下为高频P0项）：
- [ ] PDF封面是否为深蓝背景（非白底）
- [ ] 预算可视化是否为条形图（非纯文本）
- [ ] 红线清单是否有视觉区分（非普通列表）
- [ ] 四章结构完整：技术参数 / 红线清单 / 验收标准 / 商家评审表
- [ ] 业主是否能直接用此文件与商家谈判（无需翻译）

**Step 2：架构师视角（规格合规性）**
- [ ] Rw计算值是否在合理区间（非对称中空上限≤35dB）
- [ ] 热工参数是否与输入问卷一致
- [ ] 风压计算是否在合理误差范围内
- [ ] 档位条款是否与对应档位匹配（A档不含B档要求）
- [ ] 禁用条款清单是否准确

**Step 3：交叉验证（必选步骤）**
1. 从PDF输出反向还原问卷输入
2. 手工执行关键计算（Rw / 热工 / 风压）
3. 对比系统输出与手工结果
4. 记录差异并定级（P0/P1/P2）

**Step 4：输出验收报告**
格式：
```
验收版本：vX.X.X
验收日期：YYYY-MM-DD
P0问题：[列表或"无"]
P1问题：[列表或"无"]
结论：通过 / 条件通过（P1修复后）/ 不通过（存在P0）
```

## PLAY-02：计算引擎修复

### 适用场景
发现参数计算错误时（如当前Rw边界问题）。

### 执行步骤

**Step 1：定位**
- 确认受影响的函数（`calcRw` / `calcP3` / `calcThermal`）
- 确认受影响的输入区间（如Rw 34–38dB段）
- 确认实测数据来源（引用行业标准或实测数据）

**Step 2：修复方案设计**（在此Project讨论）
- 新边界值是什么？
- 是否影响其他计算模块（如 `resolveGlassConfig()` 的仲裁输出）？
- 是否需要更新 `GLASS_LEVELS` 或 `NOISE_SCENE` 查找表？

**Step 3：实现**（移交Claude Code）
- 修改 `calculator-v2.js`
- 更新相关测试用例
- 验证125/125 passing

**Step 4：验收**
- 执行PLAY-01 Step 3（交叉验证）
- 特别验证修复区间边界案例

## PLAY-03：新功能决策

### 适用场景
评估是否将新功能纳入当前版本。

### 决策过滤器（按顺序）

**Filter 1：准确性检查**
当前是否存在已知错误未修复？→ 如有P0未解，新功能不讨论。

**Filter 2：定位合规性**
- 是否强化「工具」定位（而非变成平台）？
- 是否保持问卷9题上限？
- 是否符合L1/L2认知缺口逻辑？

**Filter 3：技术债评估**
新功能是否会与以下已知冲突交互？
- 双玻璃推荐系统（未仲裁风险）
- Rw重复计数问题
- `size_level` 语义混用

**Filter 4：优先级排序**
|  | 紧急 | 不紧急 |
|--|------|--------|
| **重要** | 立即执行 | 纳入下个sprint |
| **不重要** | 讨论后决定 | Backlog |

## PLAY-04：架构冲突处理

### 适用场景
发现两个模块/逻辑有竞争或矛盾时。

### 执行步骤

**Step 1：三方比对**
- 现有代码实现
- 技术规格文档1
- 技术规格文档2（如有）

**Step 2：冲突定性**
| 类型 | 示例 | 处理方式 |
|------|------|---------|
| 仲裁缺失 | 双玻璃系统 | 引入显式仲裁函数 |
| 重复计数 | Rw变量重叠 | 重构边界，明确职责 |
| 语义混用 | size_level | 拆分字段或重定义 |

**Step 3：方案提案**（在此Project讨论）
- 提出解决方案
- 评估对其他模块的影响
- 确认是否保持问卷9题不变

**Step 4：实现**（移交Claude Code）

## PLAY-05：L1/L2内容边界核查

### 适用场景
任何涉及L1（参数摘要卡）内容调整时。

### L1内容标准

**必须包含（引流必要）：**
- 6项核心参数（明确列示）
- 参数结论（如：您的场景需Rw≥X dB）

**不得包含（保护L2价值）：**
- 具体达标标准判断（"您当前选择是否达标"）
- 完整红线清单
- 商家评审表
- 验收标准

**检验问题：**
用户看完L1后，能否知道"我需要什么"？→ 是 ✅
用户看完L1后，能否知道"具体标准是否达标"？→ 否 ✅（如果能，L1内容过多）

## PLAY-06：产品文档更新

### 适用场景
每次重大决策、sprint结束、问题发现后。

### 更新规则

| 文件 | 更新时机 | 更新内容 |
|------|---------|---------|
| `CLAUDE.md` | 版本状态变化 / 决策变更 | 当前状态快照、已确认决策、技术债列表 |
| `CHANGELOG.md` | 每个重大决策事件后 | 新增条目，包含触发、发现、决议 |
| `PLAYBOOK.md` | 流程优化后 | 更新或新增PLAY条目 |

### CHANGELOG条目格式
```markdown
## [决策事件名称] · 日期

### 决策事件：[简要标题]
**触发**：[是什么引发了这次决策]
**发现/背景**：[关键信息]
**决议**：[最终采纳的方案]
**原则确立**（如有）：[从此事件提炼的通用原则]
```
